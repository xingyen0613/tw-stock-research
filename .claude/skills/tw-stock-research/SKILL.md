# 台股個股研究報告

產出一份**可稽核**的個股研究報告。這個 skill 的核心價值不是「寫得漂亮」，而是**每一個數字都能追回來源，而且經過第二輪獨立驗證**。寧可少寫一個數字，也不要寫一個查不到出處的數字。

## 輸入

使用者會給：
1. `{標的}` — 股票代號或公司名稱（必填）
2. `{focus}` — 想深入的產業／技術主題（選填，例如 CPU、光通訊、矽光子、液冷）

`{focus}` 沒給的話，**不要問使用者**。自己從最新一季法說會判斷 1–2 個主導營收的主題當作 focus，並在報告開頭說明「本次自動選定的產業主題為 X，因為它佔最新一季營收 Y%」。使用者若不滿意會自己說。

## 資料來源分級

所有數字都必須帶等級標籤。這是整份報告的骨架：

| 等級 | 定義 | 例子 |
|---|---|---|
| **L1 官方** | 公司自己發布的 | 公開資訊觀測站法說會 PDF／影音、財報、重大訊息、月營收公告 |
| **L2 法人／研調** | 專業機構的分析或財測 | 券商報告轉述、MoneyDJ、TrendForce、DIGITIMES |
| **L3 媒體／社群** | 二手轉述或個人觀點 | 財經媒體、CMoney、方格子、PTT、論壇 |

衝突時 **L1 > L2 > L3**，永遠不要用 L3 的數字去覆蓋 L1。

抓資料的具體路徑、各站台特性、常見坑，讀 `references/sources.md`。

## 資料新鮮度上限

除了法說會與財報的「最近 4 季」序列之外，**所有第三方資料一律以半年內為主，超過 1 年一律不用**。

| 資料類型 | 範圍 |
|---|---|
| 法說會簡報、財報、月營收 | 最近 4 季（結構性需求，不受此限） |
| 法人財測、目標價、評等 | **半年內**；找不到才放寬到 1 年，並標註發布日期 |
| 產業分析、市場規模預估 | 發布日在**半年內**；報告內容預測未來年份不受限 |
| 社群觀點、空方論述 | **半年內**，優先最近一季 |

搜尋時查詢字串一律帶當前年份或「最近」。拿到結果先看發布日期，超過 1 年的直接丟掉，不要讀進 context。**過期資料的傷害不只是浪費 token，是會讓報告寫出已經被推翻的財測。**

## 工作流程

分五個 Phase，**不要邊查邊寫**。邊查邊寫是這類報告最大的錯誤來源——後面查到的數字蓋不掉前面已經寫好的段落。

Phase A、B 全部派 subagent 執行，主對話不自己下場查資料。派工規格見下方「派工合約」。

### Phase A — 官方資料（先做完，再做別的）

分成三個獨立可平行的子任務：

**A-1 法說會簡報（Haiku）** — 找到公開資訊觀測站的法人說明會一覽表，下載**最近 4 季**的簡報 PDF，逐份跑 `pdftotext -layout` 落成 `.txt`。**只回報檔案路徑與每份的頁數／日期，不要把內容貼回來。**

**A-2 量化財務（Haiku）** — 走 FinMind API 抓：逐季損益（營收、毛利、營益、淨利、EPS）、資產負債、現金流、月營收、PER。財務比率（流動比、速動比、負債比、ROE、每股淨值）用抓到的原始科目自己算，不要另外去搜尋。落成 `financials.json`。做法見 `references/sources.md` 的 FinMind 段。

**A-3 業務別拆解（Sonnet）** — 讀 A-1 產出的 `.txt`，抽出各業務／產品別營收占比、公司財測、關鍵發言，落成 `segments.json`。跨季分類定義若有變動，在 `note` 記下原始分類名稱。

法說會 Q&A 屬於 Phase B（簡報 PDF 幾乎不含 Q&A，只能從逐字稿、影音摘要或現場報導取得，是 L2/L3）。

**若某公司一年只開一次法說會**，或某季沒有業務別揭露，就誠實寫「該季未揭露」，圖表留空白，不要內插。

### Phase B — 非官方分析（三個 Sonnet agent 平行）

**B-1 法人財測** — 目標價、當年度／次年度 EPS 預估、營收預估、評等；以及**官方不揭露的拆解**（業務別毛利率、業務別營收預估、單一產品 ASP、市占率）。這些幾乎不會是 L1，全部歸到非官方區。

**B-2 產業分析** — `{focus}` 相關的產業分析（研調機構、券商產業報告、專業媒體）。

**B-3 空方與 Q&A** — 社群／論壇的反面意見與風險論述，以及法說會 Q&A 轉述。**一定要找空方觀點**，只有多方的報告是壞報告。

三者都受上方「資料新鮮度上限」約束，各自落成一個 JSON 檔，回報路徑與摘要。

### Phase C — 結構化（主對話自己做，強制中間產物）

把 Phase A、B 各 agent 產出的 JSON 檔合併成一份 `data.json`。這一步是防幻覺的核心：先把數字釘死，再渲染，不要一邊回憶一邊畫圖。

**合併用腳本做，不要把來源 JSON 全部 Read 進 context 再手工拼。** 寫一支 Python 讀那幾個檔、合併、輸出 `data.json`，然後只 Read 合併後的摘要（例如 `jq '.datapoints | group_by(.tier) | map({tier:.[0].tier, n:length})'`）確認筆數與分級分布。主對話需要判斷的是分級對不對、有沒有衝突，不是逐筆抄寫。

```json
{
  "meta": { "ticker": "3533", "name": "嘉澤", "focus": "CPU", "as_of": "2026-08-12" },
  "datapoints": [
    {
      "id": "dp001",
      "period": "2026Q1",
      "segment": "伺服器",
      "metric": "revenue_share",
      "value": 51.02,
      "unit": "%",
      "tier": "L1",
      "source_url": "https://...",
      "source_name": "2026/05/14 法說會簡報",
      "source_date": "2026-05-14",
      "is_estimate": false,
      "note": ""
    }
  ]
}
```

`segment` 為公司整體時填 `"company"`。`is_estimate: true` 代表是預測或推估值，不是已實現數字。

**業務別分類在不同季度會變**（某季把子公司併進「其他」之類）。遇到這種情況，在 `note` 註明原始分類名稱，並在報告的圖表下方加一行說明，不要硬套成同一個分類。

### Phase D — 驗證（Opus subagent）

開一個 subagent 做獨立驗證，指示讀 `agents/verifier.md`。把 `data.json` 與 Phase A 產出的 `.txt` 路徑一起交給它。

**驗證 agent 回溯 L1 來源時，讀的是那些 `.txt`，不是 PDF 原檔、更不是頁面截圖。** 需要確認某個數字時用 `grep -n` 定位，只讀命中的前後幾行。驗證跑一次就好，不要因為結果不滿意重派——不滿意就把具體問題補進派工 prompt 再跑，重派整輪是雙倍成本。

它回傳「通過」或「疑慮清單」。**有疑慮的項目不要偷偷刪掉**，而是：
- 能修正的就修正，並在驗證紀錄區寫明修正了什麼
- 修不掉的就從主報告移到「最新未驗證動態」區，或直接標紅註明「來源互相矛盾」

驗證沒跑完，不要輸出報告。

### Phase E — 輸出與用量回報

單檔 HTML 寫到**專案根目錄**的 `reports/`（既有報告所在的那個），用 `SendUserFile` 送給使用者（`display: "render"`）。

**不要寫到 skill 自己的目錄底下。** 寫檔前先確認 cwd 是專案根目錄，或直接用絕對路徑——
曾經發生過報告被寫到 `.claude/skills/tw-stock-research/reports/` 的情形。

**不要用瀏覽器工具開來截圖確認。** 一張截圖約 35K token，而使用者從 SendUserFile 看到的畫面完全一樣。要自查渲染有沒有壞，用 `grep` 確認這四件事就夠：

```bash
grep -c "new Chart" report.html          # 應為 4
grep -o 'id="c[0-9]"' report.html        # canvas id 齊全
grep -c "{{" report.html                 # 應為 0，佔位符全部替換完
grep -o 'data-report="[^"]*"' report.html # 應為實際的 代號-日期，不是 {{}}
```

最後一項最容易漏：`data-report` 是個人筆記存在瀏覽器裡的 key，沒填的話不同報告的筆記會互相覆蓋。

報告底部的「個人筆記」與「匯出與分享」是模板內建功能，**照抄即可，不要改動那段 JS，也不要幫使用者預填筆記內容。**

「發送到 TG」按鈕會打本機的 `scripts/tg_bridge.py`（見下節），報告本身不含任何 bot token。使用者若說按鈕沒反應，先確認他是不是直接雙擊開檔——按鈕要從 `http://127.0.0.1:8787` 開啟的報告才保證能用。

報告送出後，跑用量統計並把表格直接貼在 session 中回覆給使用者：

```bash
python3 .claude/skills/tw-stock-research/scripts/token_report.py --tools
```

回報時附一句話說明這次最大的消耗來自哪個階段，以及有沒有異常（例如某個 agent 的工具回傳體積超過 100K chars，就是有東西被整份讀進 context 了）。

## PDF 處理鐵則

法說會簡報是本報告最核心的資料，也是最容易把 token 燒光的地方。**實測：同一頁用 `pdftotext -layout` 是 980 token，轉成 PNG 讀進來是 145,000 token——148 倍。**

1. **一律先 `pdftotext -layout`**，整份轉成 `.txt` 存檔。業務別營收占比那種表格，`-layout` 能完整保留欄位對齊。
2. **不要把整份 `.txt` 讀進 context。** 先 `grep -n` 找關鍵字（`營收比重`、`Revenue share`、`Business Coverage`、`Outlook`、`Guidance`）定位頁碼，再用 `sed -n 'X,Yp'` 或 `Read` 的 `offset`/`limit` 只取那一段。
3. **只有 `pdftotext` 抽不出東西時**（純圖片型簡報、掃描檔）才轉圖，而且：單頁、`-r 100`、只轉需要的那一頁、看完即刪。轉圖前先說明為什麼非轉不可。
4. **禁止對同一頁重複轉圖或重複 Read。** 需要再看，回去讀 `.txt`。

## 模型分配

派 subagent 時用 Agent tool 的 `model` 參數明確指定，不要靠預設：

| 階段 | 工作性質 | 模型 |
|---|---|---|
| A-1 PDF 下載與 `pdftotext` | 機械執行，成敗可驗證 | `haiku` |
| A-2 FinMind 量化財務 | API 調用，有 schema | `haiku` |
| A-3 業務別拆解 | 要判斷跨季分類是否一致 | `sonnet` |
| B-1 法人財測 | 要辨識「哪一家、何時、什麼假設」 | `sonnet` |
| B-2 產業分析 | 需綜合理解 | `sonnet` |
| B-3 空方與 Q&A | 要判斷論述品質 | `sonnet` |
| C 結構化與分級 | 報告可信度的核心 | **主對話自己做** |
| D 驗證找錯 | 對抗性推理 | `opus` |

Haiku 錯一次就升 Sonnet，不要在 Haiku 上重試第二次。

## 派工合約（每個 subagent 的 prompt 都要有）

**回報格式是硬性要求，寫在 prompt 最後、用粗體標示：**

> 回報只能包含：(1) 3–8 行結論摘要；(2) 產出檔案的絕對路徑；(3) 沒查到的項目清單。
> **禁止把 JSON 內容、網頁原文、PDF 全文、表格資料貼回來。** 主對話會自己去讀檔案。

這是主對話 context 膨脹的頭號來源——一個 agent 把 60KB 的 JSON 貼回來，主對話後續每一個 turn 都要重讀它一次。

其餘三件套照 `~/.claude/docs/delegation-templates.md`：目標與動機、驗收條件、回報格式。另外每個 prompt 都要帶上今天日期與「資料新鮮度上限」那張表。

## 輸出

報告的完整章節規格、每一區該放什麼、四張圖表的定義，讀 `references/report-structure.md`。
HTML 模板、配色與 Chart.js 用法，讀 `assets/report-template.html`。

## 發送到 Telegram

報告裡的「發送到 TG」按鈕需要本機服務 `scripts/tg_bridge.py` 在跑：

```bash
python3 .claude/skills/tw-stock-research/scripts/tg_bridge.py
```

然後從 `http://127.0.0.1:8787` 開報告（不是雙擊檔案）。服務會用 headless Chrome 把報告印成 PDF，
連同筆記與章節勾選一起帶進去，再用 Bot API `sendDocument` 發到設定好的頻道。
bot token 存在 `~/.config/tw-stock-tg/config.json`，**永遠不進報告 HTML、不進 repo**。

舊報告（沒有按鈕的）用 CLI 發：`python3 …/tg_bridge.py --send reports/xxx.html`。

設定步驟、bot 權限、錯誤訊息對照，讀 `references/telegram-sending.md`。

## 三條不可妥協的規則

**1. 查不到就寫查不到。** 禁止用產業平均、同業數字、或前後季內插來補洞。空白的圖表比錯的圖表有價值。

**2. 官方區只放 L1。** 業務別毛利率、業務別 EPS 這類台股公司幾乎從不揭露的東西，不管找到多合理的推估，都只能放在非官方分析區，而且要標明是誰推估的。

**3. 主報告只放已驗證的。** 剛出爐、只有單一來源、還沒有第二方佐證的消息（例如當天剛開完董事會的財報數字），放進「最新未驗證動態」區塊，不要混進主報告的表格與圖表。

## 報告免責

報告結尾固定加上：資料整理自公開來源，正式數據以公開資訊觀測站公告為準，本報告不構成投資建議。
